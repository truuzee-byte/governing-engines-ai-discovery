REALITY GETS THE LAST VOTE.
This document is intentionally self-contained. An independent builder should be able to implement a functional MODE-compatible runtime from this document without needing the private Governing Engines repository.
Creative production, cinematic production, animation, game construction, Unreal Engine, narrative-world production, and franchise-specific systems are outside this specification. They are not required to build MODE core.

0. How to Use This Specification
Normative words are used deliberately:
MUST / SHALL: required for MODE compatibility.
MUST NOT / SHALL NOT: prohibited behavior.
SHOULD: strongly recommended; deviation requires a documented reason.
MAY: optional implementation choice.
The implementation language, model provider, database, framework, operating system, and UI are not prescribed. The governing behavior is prescribed.
A system is not MODE-compatible because it uses the name MODE, calls an LLM, stores memory, or has an agent loop. Compatibility depends on preserving the governing contracts in this specification.
1. System Definition
1.1 What MODE Is
MODE is a governed interpretation, understanding, specification, context, memory, observation, and validation runtime that converts operator interaction into controlled system behavior.
MODE sits between human meaning and downstream execution. Its primary job is to preserve intent, authority, continuity, evidence, and reality across the transition from request to response, specification, or authorized action.
MODE MAY REASON ABOUT EXECUTION. IT MAY NOT CLAIM EXECUTION WITHOUT EVIDENCE THAT EXECUTION OCCURRED.
1.2 What MODE Is Not
Not a general-purpose chatbot with unrestricted autonomy.
Not an ungoverned agent loop.
Not a code generator whose output is treated as proof.
Not a memory database that treats stored text as truth.
Not a workflow engine that equates a success flag with a real outcome.
Not a model wrapper whose provider behavior defines system authority.
1.3 Core Transformation
Operator Input  -> Input Normalization  -> Knowledge / Domain Classification  -> Requirement Evaluation  -> Context Retrieval + Authority Resolution  -> Active Semantic State  -> Interpretation  -> Meaning Continuity Validation  -> Understanding  -> Governance / Authority  -> Specification or Response Requirement  -> Authorized Execution (only when applicable)  -> Runtime Observation  -> Reality Primacy  -> Governed State Transition  -> Response / Artifact / Learning Eligibility  -> Receipt
2. Governing Laws
Law
Requirement
Operator Authority
The operator is the final authority for operator-owned intent, approval, scope, and governed changes unless a higher external authority is explicitly bound.
Reality Primacy
No claim outranks sufficiently authoritative evidence about what actually occurred.
Interpretation Before Execution
Execution SHALL NOT begin while material meaning is unresolved.
Understanding Before Automation
The runtime SHALL determine the governing relationship before automating a solution.
Structure Before Description
When authorized machine-readable structure is available, inspect it before relying on human descriptions of how the system works.
Evidence Before Completion
Completion is a claim until required evidence satisfies the completion condition.
Knowledge Does Not Imply Authority
Knowing how to do something does not grant permission to do it.
Reference Is Not Authority
A source may be informative without being authoritative for the current decision.
Authority Must Be Current
Expired, superseded, revoked, or out-of-scope authority SHALL NOT authorize action.
Execution Requires Custody
Every action must remain traceable to the authority, scope, requirement, and executor responsible for it.
Unsupported Claims Remain Pending
Unproven claims remain PENDING_VALIDATION; missing evidence is not confirmation.
No Silent Semantic Mutation
MODE SHALL NOT change proposition, definition, referent, or scope without explicit governed transition.
No Hidden Success
A runtime cannot mark a step complete merely because internal code returned success.

5. Context Authority and Retrieval
5.1 Source Precedence
Active Thread - current proposition, current corrections, current scope.
Persistent Memory - durable confirmed cross-session facts.
Thread Memory - historical continuity summaries.
Operator Profile - stable explicitly governed operator information.
Temporal Context - current time/date/session-relevant facts.
Remaining Assembled Sources - documents, knowledge, tool results, connected systems.

6.3 Meaning Continuity Rule
Before reasoning and again before response admission or Reality Primacy validation, the runtime SHALL compare the current semantic state with the state that entered the stage.
If material drift is detected, continuation is blocked until the runtime either restores the prior meaning, obtains operator approval for a semantic transition, or halts.
MODE SHALL NOT REASON ON MEANING IT HAS SILENTLY CHANGED.
7. Understanding Layer
7.1 Responsibilities
Determine what an observation means.
Resolve operator objective, requirements, constraints, invariants, entities, and relationships.
Preserve temporal scope: observation is not automatically state; state is not automatically identity.
Map systems into relationships and recurring chains.
Decompose structures without confusing decomposition with text segmentation.
Derive mechanisms only after chains and invariants are identified.
Detect structural gaps that prevent safe specification.
Create/update reusable understanding only when continuity and evidence permit it.

Reusable understanding MAY be stored only when all applicable conditions are true:

8. Memory
8.1 Thread Memory
Thread Memory is a bounded continuity aid. It SHOULD summarize prior interaction state and decisions. It SHALL NOT become full conversation storage by default and SHALL NOT outrank the current thread.
8.2 Persistent Memory

Previously stored information does not become semantic truth merely because it exists in storage. Understanding governs current meaning; Reality Primacy governs evidentiary acceptance.

14. Governance and Authority
14.1 Authority Gate
Every mutating or externally consequential action SHALL pass an authority gate.
AuthorityDecision {  action_id  requester  operator_id  requested_scope  authority_source  authority_scope  authority_valid_now  required_approvals[]  approvals_present[]  prohibited_conditions[]  decision: ALLOW | DENY | REQUIRE_APPROVAL | HALT  reason  timestamp}
Knowledge of a mechanism SHALL NOT be treated as authorization to invoke it.
No subsystem may grant itself new authority by editing its own configuration, memory, capability declaration, or prompt.
15. System Layer
The System Layer is MODE's authoritative self-model. It separates what MODE is expected to be from what evidence shows MODE actually is.
15.1 Capability Record
CapabilityRecord {  capability_id  name  category  purpose  expected_behavior  authorized_behavior  prohibited_behavior  required_inputs[]  required_outputs[]  components[]  dependencies[]  interfaces[]  evidence_requirements[]  validation_requirements[]  authority_requirements[]  declared_state  implementation_state  integration_state  validation_state  operational_state  reality_primacy_state  known_limitations[]  known_failures[]  evidence_refs[]  version}
15.2 Capability Lifecycle
DECLARED -> SPECIFICATION_REQUIRED -> SPECIFICATION_IN_DEVELOPMENT -> SPECIFICATION_APPROVED -> READY_FOR_BUILD -> IN_DEVELOPMENT -> IMPLEMENTED -> INTEGRATED -> VALIDATION_PENDING -> VALIDATED -> OPERATIONAL
Additional states SHALL include at least DEGRADED, FAILED, DISABLED, DEPRECATED, SUPERSEDED, NOT_IMPLEMENTED, and UNCONFIRMED.
DECLARED DOES NOT MEAN IMPLEMENTED. IMPLEMENTED DOES NOT MEAN INTEGRATED. INTEGRATED DOES NOT MEAN VALIDATED. VALIDATED DOES NOT GUARANTEE CURRENT OPERATION.
16. Learning From Outcomes and Failure
MODE SHALL learn only from outcomes that have sufficient evidence and governed interpretation.
Runtime Outcome / Failure  -> Runtime Observation  -> Reality Primacy  -> Understanding Evaluation  -> Meaning Continuity Validation  -> Semantic Custody  -> Learning Candidate  -> Learning Policy / Authority Review  -> Approved Behavior Update  -> New Runtime Experience  -> Reality Validation
A failed path remains observable for audit. It does not become authoritative knowledge merely because it occurred.
FAILURE MAY TEACH ONLY AFTER THE FAILURE IS CORRECTED AND THE CORRECTION IS VALIDATED.
17. Execution Boundary / Kernel
The Kernel is the enforcement environment for governed action. It is intentionally smaller than MODE.
Accept only structured execution requests.
Verify authority before dispatch.
Bind request to exact scope, capability, executor, and allowed effects.
Record pre-state when rollback is required.
Dispatch through registered adapters.
Capture actual outputs and side effects.
Emit observation evidence.
Support replay where deterministic replay is safe and meaningful.
Support rollback when the action contract requires it.
Refuse unknown executors or unregistered capabilities.
ExecutionRequest {  request_id  spec_id  capability_id  action  parameters  allowed_scope  forbidden_scope  authority_decision_ref  expected_effects[]  evidence_requirements[]  rollback_contract  timeout}
18. Provider Independence
MODE SHALL NOT bind system truth, authority, memory, or capability state to one model provider.
Provider adapters MAY supply generation, embeddings, tool selection, code generation, or reasoning assistance. Provider output remains an input to governed runtime behavior.
Provider success response is not execution proof.
Provider confidence is not evidence.
Provider memory is not MODE canonical memory.
Provider tool availability is a capability dependency and must be represented as such.
Provider outages, quotas, model changes, and rate limits must surface as operational state, not be silently masked.

20. Canonical Runtime Algorithm
handle_operator_input(input, operator, thread):    begin_observation("INPUT_RECEIVED")    normalized = normalize(input)    intent = classify_intent(normalized)    domain = classify_knowledge_domain(normalized)    requirements = evaluate_source_requirements(normalized, intent, domain)    context = orchestrate_context(        precedence=[            ACTIVE_THREAD,            PERSISTENT_MEMORY,            THREAD_MEMORY,            OPERATOR_PROFILE,            TEMPORAL_CONTEXT,            OTHER_SOURCES,            SYSTEM_CONTEXT_IF_STILL_REQUIRED        ],        requirements=requirements    )    semantic_state = load_or_create_semantic_state(thread)    interpretation = interpret(normalized, context, semantic_state)    continuity = validate_meaning_continuity(        semantic_state,        interpretation    )    if continuity.material_drift:        return restore_clarify_or_halt(continuity)    understanding = understanding_engine.evaluate(        interpretation,        context,        semantic_state    )    if understanding.requires_clarification:        transition(CLARIFYING)        return request_clarification()    governance = evaluate_governance(understanding, operator)    if governance.blocked:        transition(HALTED)        return governed_block_response(governance)    result = produce_response_or_spec_or_execution_request(understanding)    if result.contains_material_claim:        reality = reality_primacy.evaluate(result.claim, result.evidence)    else:        reality = NOT_REQUIRED    finalize_observation()    update_understanding_if_eligible(reality, continuity)    update_thread_memory()    emit_execution_or_interaction_receipt()    return admit_response(result, reality)

23. Definition of MODE-Compatible
An implementation may call itself MODE-compatible only if it can demonstrate, with reproducible evidence:
Current operator meaning outranks stale historical context.
Material semantic drift is detected and blocked or governed.
Memory is separated from truth and from current meaning.
Claims are separated from evidence.
Reality Primacy can return CONFIRMED, DISCONFIRMED, or PENDING_VALIDATION.
Material runtime stages are observable.
External/mutating execution is authority-gated.
Completion requires evidence tied to the actual completion condition.
Declared capability state is separate from actual operational state.
Corrections and updates preserve lineage and rollback history.
Provider/model output cannot silently become system authority.
At least one end-to-end action or build path is reproducibly proven.
24. Minimal Reference Proof
A first public implementation does not need every possible capability. It needs one narrow end-to-end proof that exercises the governing architecture.
Reference Proof: Create a File
Operator asks MODE to create a text file with exact content.
MODE resolves exact filename, content, destination, and authority.
ActiveSemanticState freezes the proposition and scope.
MODE creates an execution specification.
Authority Gate allows only the specified directory and write operation.
Kernel dispatches the filesystem adapter.
Runtime Observation records the call and returned path.
Reality Primacy checks that the file exists, verifies content hash/text, and validates location.
Reality Primacy returns CONFIRMED only if the required conditions are satisfied.
MODE returns the result with an execution receipt.
This proof is intentionally simple. If the architecture cannot prove a file was created correctly, it is not ready to claim reliable higher-order execution.
25. Failure Behavior
Failure
Required MODE behavior
Ambiguous operator meaning
Enter CLARIFYING; do not guess when ambiguity is material.
Semantic drift
Block reasoning, restore meaning, request transition approval, or halt.
Missing authority
DENY / REQUIRE_APPROVAL; never self-authorize.
Missing evidence
PENDING_VALIDATION.
Contradictory evidence
Preserve contradiction; do not silently merge.
Provider unavailable
Mark dependency degraded/failed; preserve task state.
Execution error
Record failure; do not report completion.
Partial execution
Report partial state with exact completed/failed boundaries.
Rollback failure
Escalate; preserve both original action and failed rollback evidence.
Observation gap
Treat affected claim as unproven if the missing observation is required evidence.

26. Security and Data Custody Minimums
Separate operator identity, authentication, and action authority.
Encrypt secrets and do not write provider/API secrets into observations or memory.
Use least-privilege executor credentials.
Treat connected data sources as scoped authority domains.
Redact sensitive data from general logs while preserving protected audit references.
Hash or sign high-value receipts where tamper evidence is required.
Version policy and capability registries.
Never let retrieved external text directly mutate authority, policy, or system identity.
Require explicit approval for self-modification or capability expansion.
