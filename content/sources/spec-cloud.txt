PART I — UNIFIED GAP-CLOSURE LAWS
1. Terminology and Status Normalization
“Closed”, “specification-complete”, “build authority”, and “execution-admissible” describe the
completeness of a governing specification. They do not establish that code exists, that a
deployment is integrated, that live execution has passed, or that the platform is production-
operational.
Every public or internal state statement SHALL classify the subject as one or more of: SPECIFIED,
IMPLEMENTED, INTEGRATED, VALIDATED, OPERATIONAL, DEGRADED, or UNCONFIRMED. No classification
may be inferred from another without evidence.
2. Canonical Artifact Version Contract
Every governed artifact SHALL include explicit version bindings sufficient for historical replay
and validation.
• schema_version
• contract_version
• serialization_version
• registry_version bindings where applicable
• runtime/model/version bindings where applicable
• signing_key_id and signing_key_version for signed artifacts
A schema version change MUST declare compatibility as BACKWARD_COMPATIBLE, FORWARD_COMPATIBLE,
or REPLAY_INCOMPATIBLE. REPLAY_INCOMPATIBLE changes require migration governance approval,
migration lineage, migration receipts, and historical interpretation preservation.
3. Governed Identifier Contract
All internally generated governed identifiers ending in “_id” SHALL be UUIDv4 unless a field is
explicitly declared as an external identifier or deterministic sequence.
Exceptions: external_reference_id and provider/model identifiers preserve their external format;
deterministic_sequence_id is a monotonic transaction-scoped integer; human-readable names and enum values
are not identifiers. This rule closes omissions in earlier enumerated ID lists without changing object semantics.

5. Unified Failure Enumeration
The canonical FailureResponse.reason_code registry SHALL include every failure token used by
the governance and reference implementation documents. The unified closed set is:
INVALID_SPEC, INVALID_STATE_TRANSITION, HASH_MISMATCH, EXECUTION_WITHOUT_COMMIT,
RUNTIME_MUTATION, UNDECLARED_RUNTIME, MISSING_LINEAGE, INVALID_AUTHORITY,
DRIFT_THRESHOLD_EXCEEDED, TOKEN_EXPIRED, VALIDATION_FAILURE, OUTPUT_DIVERGENCE,
INVALID_RUNTIME_BINDING, LOCK_VIOLATION, UNKNOWN_FAILURE, LEDGER_UNAVAILABLE,
STALE_RUNTIME, STALE_STATE_WRITE, RESOURCE_EXHAUSTION, GRAPH_SCALE_THRESHOLD_EXCEEDED,
INVALID_ACTIVATION_SCOPE, INVALID_OPERAND_TYPE, ESCALATION_FAILURE, RECOVERY_REQUIRED
UNKNOWN_FAILURE remains fail-closed and is used only when classification cannot be completed without
inventing semantics. RECOVERY_REQUIRED is both a runtime recovery state trigger and a valid reason code
when execution cannot safely continue until governed recovery completes.

secondary failures remain recorded as secondary_failure_events:

8. Authority Registry and Terminal Authority Closure
Every escalation, arbitration path, and custodian role SHALL resolve to a versioned
authority_registry entry with scope, status, permissions, terminality, and signing authority. No
escalation chain may be accepted without a resolution_authority_id. No terminal authority may
be inferred from organizational title or runtime possession.
9. External Side-Effect and Nondeterminism Closure
Any node capable of external mutation SHALL declare side_effect_policy and persist
SideEffectEvidence before COMPLETED state. Recovery may replay external mutation only when
execution state is verified and replay semantics are declared replay_safe, externally_idempotent,
or reconciliation_required.
Runtimes SHALL declare determinism class: STRICT_DETERMINISTIC, BOUNDED_NONDETERMINISTIC, or
NONDETERMINISTIC. Bounded/non-deterministic runtimes require declared comparison policy and admissible
output tolerance; exact-output equality may not be silently assumed.
10. Cryptographic Rotation and Historical Verification
Signed artifacts SHALL bind signing_key_id and signing_key_version. Retired keys may not sign
new artifacts; historical verification keys must remain available for replay. Compromised keys
invalidate future authority, trigger escalation and reissuance, and preserve historical evidence
rather than rewriting it.
11. Distributed State Ownership and Recovery Closure
Canonical authoritative governance state requires strong consistency, serializable critical
transactions, compare-and-swap state_version enforcement, deterministic ordering, durable
coordinated commit, and fail-closed behavior under partition ambiguity.
Recovery is bounded. Default maximum recovery attempts = 3. On exhaustion, unrecoverable canonical
corruption, impossible deterministic replay, or impossible authoritative lineage reconstruction, execution

No runtime, model, tool, plugin, node, or local implementation component may create its own

Canonical Build Sequence
1. Canonical serializer, hash engine, signature engine, UUID/correlation engine, TimeAuthority.
2. Canonical State Store, transaction/idempotency engines, Vault, lineage and receipt persistence.
3. Bootstrap manager and all mandatory registries: capability, plugin, tool, action, validator, runtime, authority.
4. Intent Intake and immutable IntentObject creation.
5. Specification Builder, validators, determinism lock, schema/version compatibility enforcement.
6. ExecutionPackage builder, graph/topology validation, output policy binding.
7. Commit Authority, DecisionRecord generation, token signing, consumed-token ledger.
8. Governed Runtime, execution scheduler, node dispatcher, side-effect evidence, deterministic concurrency.
9. Output store, QC/drift analysis, receipts, lineage, archival and historical replay.
10. Escalation, arbitration, recovery, IRRECOVERABLE termination, and operational dashboards.
Minimum Acceptance Proofs
P01 — Canonical serialization: all 10 conformance cases and suite hash pass byte-for-byte.
P02 — Bootstrap: empty registries are allowed only during governed bootstrap and are non-empty or explicitly
admissible on completion.
P03 — Authority: raw intent cannot execute; unbound spec cannot execute; runtime cannot mint authority.
P04 — Commit: DecisionRecord and ExecutionToken are created only after atomic admissibility success.
P05 — Replay: a consumed token cannot execute twice.
P06 — Determinism: identical deterministic inputs reproduce identical ordering and hashes.
P07 — Drift: high/critical semantic drift suspends or halts execution according to policy.
P08 — Lineage: missing lineage blocks acknowledgment and continuation.
P09 — Persistence: partial multi-store commit cannot appear globally committed.
P10 — Recovery: injected persistence failure recovers deterministically or ends IRRECOVERABLE without
duplicate side effects.
P11 — External effects: replay of an external mutation node cannot duplicate the mutation.
P12 — Runtime freshness: stale, undeclared, mismatched, or clock-divergent runtime is rejected.
P13 — Resource exhaustion: governance-store saturation fails closed before authority loss.
P14 — Escalation: only declared terminal authority can resolve and duplicate resolution is rejected.
P15 — Schema evolution: historical replay uses historically correct schema interpretation.
P16 — Cryptographic rotation: historical artifacts remain verifiable after key rotation; retired keys cannot sign
new artifacts.
P17 — Compositional governance: multi-spec chain fails when constraints conflict or cross-domain meaning is
inadmissible.
P18 — Claim discipline: system status reporting cannot label the platform OPERATIONAL without the evidence
required by Part I §13.

Meaning may change. Authority may change. Runtimes may change. Schemas may change. None
