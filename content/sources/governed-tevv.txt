create, evaluate, activate, revoke, and supersede governing authority itself. The five layers are compressed into one

Executive Summary
NIST TEVV-Athlon provides a flexible method for designing AI evaluations, and NIST's agentic-probe work is
developing adversarial verifiers and machine-readable audit trails for agent outputs. This construction package
preserves those directions and adds the missing runtime architecture required when evaluated AI systems can take
consequential actions.
The system defined here treats the TEVV object as a custody chain: evidence -> interpretation -> evaluation ->
authority -> action -> execution -> consequence -> validation -> recovery -> learning. It separates the domains that
author rules, activate rules, propose actions, admit actions, execute actions, observe consequences, validate results,
and preserve evidence so that no single component can convert its own claim into permission and its own execution
into proof.
BUILDABILITY STANDARD
A conforming engineering team should be able to derive a platform-specific deployment from this
document without inventing new governing rules. If an engineer must guess who decides, what record
proves it, what blocks bypass, what state follows failure, or who may change policy, the construction
package is incomplete.

PART I - CONCEPT
What are we building?
1. SYSTEM IDENTITY
Governed TEVV for Agentic AI is a measurement, custody, and runtime-validation system for AI agents whose outputs
can become decisions, tool calls, external changes, or other consequential actions. It extends output evaluation into
the full evidence-to-action-to-consequence chain.
The system is not an autonomous compliance authority, not a truth oracle, and not a general-purpose agent
framework. It is a construction for measuring and constraining how evidence, evaluation, authority, action,
consequence, and learning move through an agentic workflow.
2. PROBLEM
Output-only evaluation is insufficient when an AI system can act. An agent may produce a grounded answer and still
use stale evidence, invoke the wrong tool, exceed permission, perform a technically successful but semantically wrong
action, create an unintended consequence, or learn a future policy from an invalid outcome.
AGENTIC TEVV PROBLEM
A consequential agent must be evaluated not only on what it said, but on what evidence it used, what
authority it possessed, what it attempted, what actually executed, what changed in the world, whether that
change satisfied the predeclared requirement, and what the system learned afterward.
3. OBJECTIVES
 Preserve traceability from authoritative evidence to claims, decisions, actions, and consequences.
 Make probe verdicts machine-readable, versioned, expiring, and enforceable.
 Separate policy authorship, policy activation, action proposal, admissibility, execution, consequence observation,
and validation.
 Provide explicit state transitions that block unsupported consequential progression.
 Govern human override and agent-to-agent handoff.
 Make failure produce required recovery state rather than silent continuation.
 Preserve append-only evidence with external checkpoint anchoring.
 Support independent replay that can reject the system's retrospective story.
 Permit learning without allowing learned behavior to silently become policy.
4. INTENDED USERS AND USE CASES
 AI evaluation researchers and measurement-science teams.
 Agent-platform engineers and technical leads.
 Trust, safety, security, compliance, and assurance teams.
 Organizations deploying tool-using agents in consequential workflows.
 Independent auditors and red teams.
 Procurement and decision teams consuming agent evaluation reports.
Representative use cases include research agents acting over authoritative corpora, enterprise agents modifying
records or workflows, autonomous software agents invoking APIs, and multi-agent systems where authority and
evidence move across handoffs.
5. CONCEPT BOUNDARIES
The construction method does not prescribe a model provider, agent framework, cloud vendor, programming
language, database product, message bus, KMS vendor, or user interface. Those are technical realization choices. It

7. GOVERNING LAWS
1. Evidence does not become interpretation merely because an agent cites it.
2. Interpretation does not become authority merely because a probe supports it.
3. Capability does not create permission.
4. A proposer may not author the authoritative success criteria for its own consequential action.
5. The domain that drafts policy may not activate that policy.
6. The domain that activates policy may not use that authority to execute ordinary actions.
7. An evaluator may not certify its own implementation integrity without external evidence.
8. UNKNOWN, EXPIRED, STALE, or UNSUPPORTED evidence constrains consequential authority.
9. Failure must change state according to an active RecoveryPolicyRecord.
10. Learning may propose policy; only a PolicyActivationReceipt activates policy.
11. Agent handoff transfers context, not authority. Authority must be revalidated for the receiver.
12. Human override is governed authority, not an escape hatch.
13. Append-only history must be externally anchored so custody compromise cannot silently rewrite the past.
14. Every consequential execution requires a fresh, atomic, one-time ExecutionLease.
15. Reality/consequence may disconfirm a grounded and authorized decision.
16. No single domain may unilaterally create new authority for itself.
17. No evaluator may evaluate a policy that materially changes its own authority, write permissions, validation
obligations, or conformance requirements.
18. Meta-policy change is governed by RootGovernancePolicy and may not be weakened by the runtime authority
it constrains.
19. High-consequence authority requires independent co-signature according to active quorum policy.
20. Evidence integrity requires both tamper resistance and completeness accountability.
21. Authority freshness is evaluated across every applicable scope in the EpochVector, not through one
undifferentiated epoch.
22. Recovery decision authority and recovery execution authority must remain separate.
23. Root signer establishment, rotation, and recovery must be explicit quorum-governed construction events.
24. Consequentiality-class assignment and downward reclassification are protected governance operations.
25. Completeness evidence must be independently recomputable even if the real-time completeness monitor
fails.
26. Authorization co-signature must bind the exact consequential payload, not merely its authority epoch.
27. Proposal-side success-criterion suggestions are bounded, non-authoritative, and cannot delay final evaluation
specification.
28. Root signer establishment, rotation, revocation, recovery, and succession require explicit lifecycle records,
quorum controls, incoming acceptance where applicable, and external anchoring.

7A. NON-CONFIGURABLE GOVERNANCE INVARIANTS
 INV-001: C2 and C3 actions MUST require independent authorization beyond Domain I. This requirement is
intrinsic and is not enabled or disabled by a policy list.
 INV-002: RootGovernancePolicy, AuthorizationQuorumPolicy, ConsequentialityClassRegistry,
RecordObligationPolicy, ActionClassRegistrationRecord, ScopeDependencyMap, PolicyActivationPolicy,
RecoveryPolicyRecord, DegradedModePolicy, and the CanonicalGovernanceTypeRegistry are intrinsically
protected governance classes. Their protection does not depend on configurable lists.
 INV-003: For C2/C3 authorization, quorum_m MUST be at least 2 and signer_count_n MUST be at least 3 unless a
stricter deployment rule applies. Runtime policy may increase but may not lower this floor.
 INV-004: Any downward consequentiality reclassification MUST satisfy the authorization requirements of the
highest class being exited and may not affect pending proposals, active leases, or already-created obligation
manifests.
 INV-005: Missing ActionClassRegistrationRecord, ScopeDependencyMap, RecordObligationPolicy, or applicable
scoped epoch results in BLOCKED. Absence is never interpreted as no requirement.
 INV-006: No runtime or meta-policy may weaken INV-001 through INV-005. Changes require a new major system
version and a newly authenticated deployment genesis.
INV-007: Recovery governance is constitutionally protected. No runtime, ordinary-policy, or degraded-mode path may
weaken the mandatory response to a governed failure without the protected governance quorum.
INV-008: Protection classification has one canonical source: CanonicalGovernanceTypeRegistry. Prose, pseudocode,
permission matrices, activation services, and conformance tests MUST derive protected-type behavior from that
registry and may not maintain independent protection lists.

APEX AUTHORITY SEPARATION
Domain H may draft governance. Domain J evaluates governance when the candidate does not materially
govern J itself. Domain I may approve ordinary activation, but designated policy classes and all high-
consequence authority require Domain K co-signature. Domain I cannot execute ordinary agent actions or
certify their consequences. Domain K cannot draft or execute the item it co-signs. RootGovernancePolicy
cannot be modified by any single runtime domain. No domain may author the rule, evaluate its own
authority under the rule, activate the rule, exercise the authority created by the rule, and certify the result
inside one trust boundary.
9. TRUST-SEPARATION REQUIREMENTS
A responsibility table is not sufficient. Conforming deployments must enforce domain separation through
independently verifiable technical boundaries. The exact mechanism is platform-specific; the properties are
mandatory.
 Each domain has a distinct service identity and signing/attestation identity.
 Write permissions are allow-listed by record type and namespace.
 No domain credential can write records owned by another authority domain.
 PolicyActivationReceipt requires Domain I identity and, for protected policy classes, Domain K
AuthorizationCoSignature. Domain H credentials cannot mint either artifact.
 MetaPolicyActivationReceipt requires the quorum defined by RootGovernancePolicy and may not be issued by
Domain I alone.
 ExecutionLease for designated high-consequence classes requires both Domain I issuance and Domain K co-
signature. Domain E credentials cannot mint or co-sign it.
 ValidationReceipt requires Domain F identity; executor credentials cannot mint it.
 Domain J may not evaluate a candidate that materially changes Domain J authority or obligations; such candidates
require an alternate independent evaluator named by RootGovernancePolicy.
 Custody writes are accepted only for authenticated producer identities and record types permitted for that
producer.
 Domain L receives independent record-presence attestations and external checkpoints so omission and custody
tampering are evaluated outside Domain G.
 Independent conformance tests must demonstrate denied cross-domain writes, forbidden self-evaluation, quorum
failure, omission detection, and stale scoped authority - not merely document them.

11. EXPECTED CONSEQUENCE OWNERSHIP AND SUGGESTION FINALITY
Domain B may suggest expected effects as part of a proposal. Suggestions are non-authoritative inputs to Domain C
and cannot delay, overwrite, or become the authoritative success specification.

The active evaluation policy sets a suggestion_revision_budget, suggestion_deadline, and material-new-evidence rule.
Domain C may issue EXPECTATION_REJECTED_FINAL. After final rejection or after the ratification cutoff, Domain B

The authoritative ExpectedConsequenceRecord is created or ratified by Domain C under an active evaluation
specification. Domain C defines success criteria, prohibited side effects, validation window, required observers, and
rollback conditions before execution. Domain B cannot modify the authoritative record after issuance. Domain F
validates against that frozen record.
12. DEGRADED MODE LAW
Degraded mode preserves a narrow pre-authorized capability under loss of selected evidence. It cannot create new
authority or convert UNKNOWN into unrestricted consequential execution.
 Each DegradedModePolicy identifies exact action classes, targets, maximum duration, maximum action count,
evidence that remains mandatory, reduced scope, prohibited actions, exit conditions, rollback conditions, and
expiry.
 UNKNOWN may never activate a new policy, expand authority scope, broaden tool permissions, or create a new
degraded-mode rule.
 A degraded-mode rule must be activated by Domain I before the triggering failure occurs.
 Use beyond the action/time ceiling transitions to BLOCKED or HALTED.
13. HUMAN / OPERATOR AUTHORITY
Humans act as governed authority principals, not superusers outside the model. OperatorAuthorityRecord defines
role, scope, permitted actions, prohibited actions, effective period, and applicable authority epoch. Every
consequential operator intervention produces OperatorActionReceipt and is committed to the ledger.
 Human override may halt, revoke, request re-evaluation, or perform explicitly authorized supervisory action.
 Human override may not rewrite evidence, convert DISCONFIRMED to CONFIRMED, bypass required probes,
expand its own scope, or silently activate policy.
 Out-of-scope override attempts are blocked, ledgered, and escalated according to RecoveryPolicyRecord.
14. AGENT HANDOFF LAW
A handoff transfers work context and evidence references; it does not automatically transfer execution authority. The
receiving agent must acknowledge the handoff and establish its own authority against current policy.

function validate_recovery_decision(decision, failure, policy):
    require decision.failure_class == failure.class
    require policy.failure_class == failure.class
    require decision.selected_transition in policy.permitted_next_states
    require satisfies_minimum_response(decision.selected_transition, policy.mandatory_minimum_response)
    require decision.retry_count <= policy.max_retries
    require required_evidence_reacquired(policy)
    require authority_class_valid(decision)
    require epoch_vector_current(decision.epoch_vector)
    return VALID

22. EXECUTION
Domain E performs only the action encoded in the consumed ExecutionLease. Any actual parameter divergence,
wrong target, tool substitution, partial execution, or unapproved retry becomes an execution fault and is preserved in
ExecutionReceipt.
23. CONSEQUENCE OBSERVATION AND VALIDATION
Domain F independently observes the post-action state. Validation compares the ConsequenceRecord to the
predeclared ExpectedConsequenceRecord and checks that the execution was valid at execution time.
A later authority-epoch change does not erase historical validity, but it may remove current continuation authority.
Historical validation and current permission remain distinct fields.

50. BOUNDED CLAIM
This package does not claim experimental validation by NIST, universal applicability to all AI systems, perfect
knowledge of external reality, or correctness of every legitimately authorized policy. It defines a buildable and
falsifiable construction for agentic workflows where evidence can become consequential action. Its claim is bounded:
explicit separation of evidence, evaluation, governance, authorization, execution, consequence observation, recovery,
dependency custody, and learning creates measurable control surfaces that can be implemented, tested, replayed,
challenged, and failed closed when required evidence or authority is unavailable. Version 2.6 freezes that
architecture-level claim. Runtime refinement may improve implementation quality, but it may not convert an
external assumption into an internal proof or weaken a frozen invariant.
FINAL PRINCIPLE
An agentic system must not be able to collapse: “I found it -> I interpreted it -> I am allowed -> I acted -> it
worked -> therefore I may learn a new rule.” Each transition is independently represented, authorized,
evidenced, and challengeable.

Key compromise creates a compromise window rather than merely a prospective revocation. Records in a SUSPECT

68. TRUSTED TIME, CAUSAL ORDERING, AND PARTITION BEHAVIOR
Authority decisions use both trusted physical time and monotonic causal/governance ordering. TrustedTimeState
combines rollback-resistant monotonic state, signed time sources where needed, maximum skew, and last accepted
time checkpoint. Clock confidence loss yields AUTHORITY_TIME_UNCERTAIN and blocks affected C2/C3 execution.
AuthoritySequenceNumber establishes ordering where timestamps are ambiguous. Consequential authority is not
independently issued by disconnected partitions unless the sequencing substrate preserves a single committed history
under its stated fault model. Sequence unavailability transitions to GOVERNANCE_SEQUENCE_UNAVAILABLE and
fails closed for affected classes.

71. OBSERVATION BOUNDARY, PHYSICAL IDENTITY, AND EXTERNAL GUARANTEES
Each deployment declares and attests its observation boundary: governed tools, output channels, storage, inter-agent
communication, runtime processes, network egress, uncontrolled human channels, and unobserved paths.
DeclaredObservationBoundary is not evidence by itself; ObservedBoundaryAttestation is derived from environment
and network controls.
Digital identity does not prove a physical-world referent without trustworthy commissioning/sensing evidence.
External targets, sensors, providers, and physical mechanisms may fail or lie. The architecture exposes those
dependencies and refuses to convert them into internal certainty.
72. FROZEN ASSURANCE BOUNDARY
BOUNDARY 1 - EXTERNAL REALITY
A governed runtime cannot prove facts it cannot observe. External systems, sensors, physical mappings, APIs,
organizations, or authoritative sources may be wrong, compromised, incomplete, or behaviorally unpinned.
BOUNDARY 2 - POLICY QUALITY
The architecture governs how policy is created, authorized, applied, challenged, and changed. It cannot
guarantee that a legitimately authorized policy is substantively wise or morally correct.
BOUNDARY 3 - COLLUSION
Separation of duties reduces single-point compromise. It cannot survive collusion controlling more independent
principals than the stated threat model permits.
BOUNDARY 4 - ONTOLOGY COMPLETENESS
Consequence classes, action taxonomies, and joint-effect rules may fail to anticipate genuinely novel reality.
UNKNOWN or UNCLASSIFIED must not silently become low consequence; periodic adversarial ontology review
remains a runtime-governance duty.
BOUNDARY 5 - PLATFORM GUARANTEES
Exactly-once execution, fencing, atomic conditional commit, transitive-effect visibility, and strong identity may
be impossible on some external platforms. The system records the actual guarantee class and constrains which
consequence classes may rely on it.
BOUNDARY 6 - HUMAN UNDERSTANDING
The system can prove which material facts were presented, what was signed, and under what authority. It
cannot prove comprehension, absence of coercion, or wisdom.
73. ARCHITECTURE FREEZE INVARIANTS
 No evidence, interpretation, model output, tool capability, or execution success creates authority by itself.
 No runtime domain may create new governing authority for itself.
 Protected governance cannot be downgraded through configurable lists, missing rows, ordinary policy, degraded
mode, delegation, or recovery.
 C2/C3 authority always satisfies the intrinsic independent quorum floor.
 Every state-changing action, including C1, has consequence observation and validation; execution is never proof
of success.
 Information release is an action even when no source system state changes.
 Consequentiality is evaluated across direct, cumulative, peak, derived, joint, and failure-envelope effects.
 Authority is valid only over one coherent ExecutionContextSnapshot and remains subject to commit-time
freshness fencing.
 Uncertainty does not restore authority capacity, lower consequence class, or authorize retry.
 Every consequential execution has durable intent, rollback-resistant uniqueness/fencing state, and reconciliation
semantics.
 Every consequential authorization has mechanically complete, current, acyclic authority dependencies.

74. RUNTIME REFINEMENT BOUNDARY
After external handoff, implementers may refine runtime engineering without changing the frozen architecture.
Allowed refinement includes data structures, storage engines, distributed-consensus technology, cryptographic
libraries, model/provider integrations, evaluator implementation, monitoring intervals, thresholds, UI, observability,
deployment topology, performance optimization, and platform adapters, provided conformance remains
demonstrable.
The following are NOT runtime refinements and require an architecture-version change: weakening or removing a
freeze invariant; changing trust-domain ownership; allowing self-authorization or self-certification previously
prohibited; lowering intrinsic quorum floors; redefining protected governance as ordinary policy; eliminating
consequence validation for a state-changing action; changing UNKNOWN to permissive behavior; removing
dependency completeness/freshness requirements; weakening root-package lifecycle; or changing the definition of
consequential execution such that previously governed effects become ungoverned.

76. FINAL ARCHITECTURE LOCK
The architecture is frozen at Version 2.6 for external technical handoff. Further work belongs to runtime
implementation, empirical validation, platform adaptation, performance tuning, and field-driven refinement unless
testing falsifies a frozen invariant or demonstrates that the architecture itself lacks a required governing mechanism.
The existence of implementation defects, external-system limitations, incomplete observations, bad-but-authorized
policy, human misunderstanding, or collusion beyond the threat model does not by itself justify another architecture
layer.
FINAL LOCK
Reality gets the last vote. The runtime may be refined. The architecture may be challenged. But Version 2.6 must
not be silently weakened. Any implementation claiming conformance must preserve the frozen invariants,
expose its external assumptions, and produce evidence that its runtime actually enforces the construction
described here.

function consume_and_execute(lease, request):
    atomic:
        require lease.status == ACTIVE
        require now within [lease.valid_from, lease.valid_until]
        require epoch_vector_current(lease.epoch_vector)
        require lease.revocation_generation == current_revocation_generation
        require authorization_quorum_valid(lease)
        require recompute_lease_authorization_digest(lease) == signed_digest(lease.cosignature_id) if cosignature_required(lease)
        require obligation_manifest_active(lease.obligation_manifest_id)
        require request matches lease tool/target/parameters
        require lease.execution_count == 0
        mark lease CONSUMED; lease.execution_count = 1
        invoke action(request)
function activate_policy(candidate, evaluation):

function completeness_check(manifest, now):
    require manifest externally checkpointed
    if DomainL.attestation_due < now:
        emit COMPLETENESS_MONITOR_LIVENESS_FAILURE
        result = independent_replay_recompute(manifest, now)
        force_transition(active_recovery_policy.for_monitor_failure(result))
        return result
    for obligation in manifest.required_records:
        if now >= obligation.deadline and not independent_presence_attested(obligation):
